# Before You Go: real-provider failure audit — 7 October 2026

Local implementation only. No deployment, production data/settings writes, migration or backend restart. The one-column modal and all PDF renderers remain unchanged.

1. **Root cause and evidence.** One authorized real request using the local configured key/model and synthetic Bucharest, Romania / Panama passport / 1–3 October 2026 / Europe/Bucharest / RON context reproduced the failure: the primary request reached its 25,000 ms deadline without returning a usable response. Primary latency was **25,009 ms**, total retrieval **25,013 ms**. The provider path returned the minimal fallback. This makes the short deadline the strongest evidenced explanation for the production symptom, rather than missing destination context. Production logs/configuration were not accessed; neither the production cause nor the underlying network/provider reason for the delay is proved. No HTTP status or output arrived, so authentication/account access, request acceptance, schema rejection, tool activity and token usage cannot be inferred from this timeout.
2. **Timeout.** Yes, reproduced with a live request at the old 25-second limit. The final Essentials deadline is **45 seconds**, still capped by a shorter request-local admin `ai_timeout_seconds`. The same effective deadline is logged and passed to the wrapper. A caller AbortController now also cancels the actual fetch when the outer deadline expires; a cancelled operation cannot start a delayed fetch after quota work. Existing callers without a signal retain their existing timeout behavior. Cancellation does not prove that upstream generation/billing stops immediately. **The final 45-second request was not live-retested**, respecting the one-live-request limit; it can still fail if the provider/network takes longer.
3. **Parsing/schema.** Previously `JSON.parse(output).countries` inside a broad catch discarded the whole guide on invalid/truncated JSON, empty output, refusal or an invalid country envelope, with no diagnostic distinction. There was no whole-guide local Ajv rejection of an otherwise valid JSON response merely because one nested section was missing. However, the outbound strict schema demanded every section object and minimum phrase/customs counts, making genuinely unknown output impossible without meeting those counts. Now the root and destination objects stay required, named section values can be null, named optional fact values remain null-capable, and phrase/customs minimum counts are prompt/coverage concerns rather than a hard schema requirement. Per-section filtering preserves useful facts despite another section being absent/malformed. Invalid JSON is honestly rejected, never repaired with guessed text. Supported message content and SDK `output_text` are parsed; refusal, missing root, invalid country shape, empty output and truncation receive separate safe reasons. Valid complete JSON inside an incomplete/failed response can supply ordinary guidance; it cannot certify critical evidence.
4. **Search coupling.** `web_search`, low search context, `tool_choice:auto`, at most two built-in tool calls and source metadata remain in the same single Responses request. Search is available, not mandatory. Failed search items/page validation do not erase returned ordinary content, and only completed response/search evidence can authorize critical facts. The nonstreaming provider response is still atomic: if the request itself times out or receives an HTTP tool/configuration error, no practical JSON has returned to preserve. No second general request, repair, retry or background generation was added. The live timeout does not identify whether search was invoked or caused the delay.
5. **Configured model and output budget.** Local environment: **`gpt-5.6-terra`**. [Official model documentation](https://developers.openai.com/api/docs/models/gpt-5.6-terra) lists Responses, web search and structured outputs support, with default medium reasoning. Production requests can override this through Admin's request-local `text_model`; start diagnostics record the actual selected model, not just the environment default. The one-destination schema has 71 properties and six levels of nesting, within the published [structured-output bounds](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses). Documentation establishes feature support, not this account's live access or successful execution of this exact combined request. The old 6,500-token single-country cap also included invisible reasoning/format tokens: [OpenAI explains](https://developers.openai.com/api/docs/guides/token-counting) that these consume the output limit. The final bounded cap is **10,000 for one country, 16,000 maximum for multiple countries**. This adds headroom; actual truncation was not observed because the live request timed out before response metadata. Model, reasoning settings, credentials and global provider configuration were not changed.
6. **Snapshots/cooldown.** Existing v5 behavior was correct: failed/partial contexts have 60-second retry protection; only complete/current guides qualify for the five-minute successful-guide cooldown. A new regression check confirms an expired failed v5 snapshot permits exactly one explicit new request, becomes complete on useful new output and is replaced without deleting historical snapshots. Reads/restores still make no AI calls. No snapshot service/hash/version changes were needed.
7. **Files changed.** `server/premium-travel/essentials-provider.js`, `essentials-generation.js`, new `essentials-response.js`; narrowly scoped `server/ai.js` optional cancellation/effective timeout helper and `server/provider-errors.js` private upstream error metadata; `server/tests/destination-essentials.test.js`; new `scripts/check-live-essentials.mjs`; this report and its link in the universal-brief report. Existing unrelated edits in these files were preserved.
8. **Diagnostics.** Primary start: ISO country/passport, actual model, web-search flag, effective deadline and token cap. Response: bounded status, output-item/text-length/tool/search counts, failed search count, incomplete reason, safe error code and token/reasoning counts when returned. Parse failure: a fixed reason enum. Provider error: whitelisted class/code/network classification, upstream HTTP status and a fixed sanitized message. Timeout: deadline and elapsed time. Normalization: section names/status/fact counts and fixed rejection-reason counts. No API key, identity, private context, prompt, response body, evidence excerpt or raw error message is logged. Internal provider error metadata is non-enumerable and preserves existing public error status/copy. These console diagnostics introduce no new database store.
9. **Live-provider test performed: YES.** Exactly one invocation: `node scripts/check-live-essentials.mjs --live`. The developer-only script calls the same production retrieval/provider/schema/search path. It never calls snapshot read/write routes or establishes an authenticated request context, so existing quota/telemetry DB writers do not run. Key/model come from local server configuration; no secret is printed. Without `--live`, or without configured key/model, it makes no request.
